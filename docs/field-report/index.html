01 · Context

A voice loop has nowhere to hide

Dead air

A chat app hides a slow model behind a typing indicator. In audio, silence reads as a crash. The naive chain — speech-to-text (ASR) → LLM → text-to-speech (TTS), run one after another — took 10.7 seconds.

One tired operator

Whatever shipped had to be debuggable by one person after midnight, on a 512MB machine, for single-digit dollars.

Users re-ranked the problem

Interviews were clear: a pause is tolerable, a robotic voice is not. Chat got a latency budget; meditation got a continuity budget.

02 · Decisions · git: remove condesending tone

Prompts are production code

Persona = state machine

The prompt encodes three phases: an interview, a hand-off that must end at the app’s begin button (it forbids asking "are you ready?"), and a meditation parameterized 0→100%.

Voice direction per request

Each endpoint ships its own TTS style block: quick and warm for chat, slow with long pauses for meditation. Emotional register is a request parameter.

Prompts outrun clients

Persona iterated daily against app builds I couldn't update: unknown roles coerced server-side, message schema append-only. No session ever broke.

03 · Latency · git: worse models, faster response — 4:07 AM

Timers first, opinions second

The commit that downgraded the models also added elapsed-time logging at every await boundary. From then on, every stage of every turn reported its cost. No APM vendor: a system whose slow parts are all network calls needs nothing finer than wall-clock deltas.

The logs made the argument simple — model calls dominated the turn, everything else was noise, and anything optimized without a timer in front of it was decoration.

Decision № 4 · TTS delivery

One synthesis call, or three in parallel?

AlternativeWall timeProsody (voice mood)Verdict
Serial, single call~4.5 sone continuous moodtoo slow for chat
Parallel 3-chunk stitch~1.6 s (slowest chunk)mood resets at every seamtoo jarring for meditation
CHOSE → Both, routed per consumer1.6 s chat · 4.5 s meditationeach product gets the budget it needsshipped

MECHANISM · split at punctuation, ≥80 chars/chunk, byte-concatenate the MP3s — frames carry sync headers, decoders forgive the seams. PRICE PAID · two delivery paths to maintain and test. Field note № 1 · war stories

Vibes are per-request state

Testers reported the meditation voice changing mood mid-session, and pauses that should have stretched getting clipped. Each TTS request renders emotional tone from scratch, so chunk two came back in a different mood than chunk one — and the chunk boundaries kept landing exactly on the scripted pauses. The benchmark measured seconds; the users were hearing mood. The fix was routing, not code: chat keeps the stitch, meditation gets one unbroken call.

COMMIT · "fixing feedback around jarring changes in tone + not enough pauses" — the whole postmortem in one line.

Field note № 3 · war stories · git: lol python is weird

The always-on fix froze the randomness

# BEFORE · module scope, evaluated once per process
question = random.choice(OPENERS)
PROMPT = f"...inspo: {question}..."
# AFTER · a fresh roll per request
def build_prompt():
    q = random.choice(OPENERS)
    return instructions_with(q)

Under scale-to-zero this was invisible: every cold start re-rolled the choice, so the bug behaved like the feature. Once the machine stayed up for days, one process meant one roll — every user got the identical "random" opener until beta testers noticed the opener never changed. Two changes, each correct alone, composed into a user-visible bug. Process lifetime is part of the program's semantics — the same class of state that process recycling at scale exists to bound.

05 · The data

Quality control for a nondeterministic product

What ran · the human loop

Every prompt change hand-tested against real conversations; in-app feedback written to Firestore beside the exact transcript that produced it; 150+ beta tests feeding the same loop, led end to end. At this scale that was the right harness — and it is why the log says "prompts" four times in one night.

What was designed · the rubric

A 30-case eval scoring tone, length, phase obedience, and safety on every prompt change before deploy, with prosody-complaint rate as a first-class metric. Never shipped. Past a few hundred users, judging tone by ear stops scaling and the rubric becomes the review process.

06 · Rebuild · git: e2e full medidation works

What a 2026 rebuild deletes, and what it keeps

Deleted by realtime APIs

Turn-taking, barge-in, and speech in both directions move inside one model: the endpointing rule, the stitch, the prosody seams, and the echo loop stop existing as categories. Two of the four war stories in this talk — and the entire latency chapter — gone.

Still mine — the session gateway

Identity, spend caps, phase state, memory, safety hooks, cost metering. Vendors sell the voice; nobody sells knowing when a meditation must end at a button, or how much a user may cost you today. And the remaining problem grows 10×: realtime pricing makes 93%-TTS look quaint.

THE TRANSFERABLE METHOD · BUILD BOTH SIDES, MEASURE, DELETE THE LOSER — JUDGMENT LIVES IN THE DELETING

Appendix · Exemplar A · the migration story · extrapolated — template, not history

Moving the progress clock server-side, under clients I can't update

The stateless design let clients claim their own meditation progress — right for an MVP, wrong for money. The migration moves authority to server-issued session tokens without breaking a single old build: three phases, each gated on a measured threshold, with the old path coerced and capped until its traffic dies naturally.

AlternativeOld clientsRiskVerdict
Big-bang cutoverbreak on day onesupport burden, trustrejected
Client-gated (force update)locked out until updatechurn exactly where retention hurtsrejected
CHOSE → Dual-accept with sunset gatesnever break; age out3 weeks of dual pathsthe shape of every schema change I ship

WHY THIS STORY WORKS · the constraint is real (un-updatable clients) · every phase transition has a NUMBER as its gate · the price (3 weeks of dual code paths) is named out loud

Appendix · Exemplar C · the experiment story · extrapolated — template, not history

The retention experiment the shutdown decision deserved

The project ended on one number. The stronger version ends on a controlled readout: one variable — the app opens by recalling your last session — two cohorts, a pre-registered gate. If memory can't move day-14 by three points, the thesis dies with evidence instead of suspicion; if it can, the roadmap writes itself.

WHY THIS STORY WORKS · the hypothesis is falsifiable · the gate was chosen BEFORE the readout · either outcome produces a decision — the experiment cannot waste its own cost
